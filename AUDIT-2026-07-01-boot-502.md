# Auditoria — Incidente de 01/07/2026: API em 502 (login travado + mapa lento)

## Sintoma
Após as mudanças de 30/06–01/07, o login "ficava só carregando e a página
atualizava" e o mapa demorava demais. A API no Railway respondia
`502 — Application failed to respond` de forma consistente.

## Causa raiz
Crash-loop no **boot** da API. O commit `beac077` removeu o export
`invalidateSiteSettingsCache` de `routes/public/index.ts`, mas
`routes/users/index.ts` e `routes/system-config/index.ts` continuavam
importando-o. Em ESM, um named-import inexistente é um `SyntaxError` no
carregamento do módulo — o processo morre **antes do `listen`**, o Railway
reinicia em loop e responde 502. Login e mapa dependem 100% da API → os dois
travavam.

Pistas falsas descartadas no diagnóstico:
- `prisma migrate deploy` no start **não** era a causa: `apps/api/railway.json`
  define `startCommand: node dist/server.js`, que **sobrescreve o CMD do
  Dockerfile**. O Railway nunca rodou o migrate.
- Builds com ERRO na Vercel eram **consequência** da API estar caída (o Next
  faz fetch na API durante o SSG). Voltaram a passar sozinhos quando a API subiu.

Validação ao vivo pós-deploy: `/health` 200, login 401 p/ senha errada,
`public/properties` 200 (1012 imóveis), mapa 200, tenant inexistente → 0
imóveis (sem vazamento).

## Prevenção adicionada
`apps/api/scripts/verify-route-imports.mjs` — importa todos os módulos de rota
compilados no passo de **build** (Dockerfile + nixpacks). Um import quebrado
**falha o build**, então o Railway mantém o último deploy saudável em vez de
subir uma versão que não liga. (No Fastify o registro de rotas é lazy, então um
try/catch em runtime não pegaria esse erro — por isso a guarda é em build-time.)

## Pendências operacionais (ação manual — fora do código)

### 1. TLS do domínio `api.agoraencontrei.com.br`
O DNS aponta (CNAME) para `api-production-669c.up.railway.app`, mas o Railway
**não emitiu certificado** para o domínio custom — ele serve o cert curinga
`*.up.railway.app`, que **não cobre** `api.agoraencontrei.com.br`. Qualquer
browser que chame esse host toma erro de TLS.

**Impacto atual: nenhum para usuários** — o front usa
`https://api-production-669c.up.railway.app` diretamente (via
`NEXT_PUBLIC_API_URL`), que tem cert válido. O domínio custom está pendente e
não é usado.

**Ação (uma das duas):**
- **Concluir o domínio no Railway:** Service da API → Settings → Networking →
  Custom Domain → adicionar `api.agoraencontrei.com.br` e aguardar o Railway
  provisionar o certificado (Let's Encrypt). Confirmar o registro DNS que o
  Railway pedir. Depois, opcionalmente, apontar `NEXT_PUBLIC_API_URL` para ele.
- **Ou remover** o domínio custom se não for usado (limpa o DNS e evita
  confusão futura).

### 2. Advisory de `tar` (Dependabot)
As advisories restantes são todas de `tar@6`, que aparece **somente** na cadeia
de build do app mobile (`apps/mobile → expo → @expo/cli → cacache → tar`). Não
está no runtime de API/web. A correção (`tar@7`) é um bump major que quebraria o
Expo SDK 51 — deve ser feita junto com um upgrade do Expo, não isoladamente.

As demais vulnerabilidades (`ws`, `@xmldom/xmldom`, `js-yaml`, `send`) foram
corrigidas via `pnpm.overrides` escopados.
